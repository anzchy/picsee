# ADR-005：全局内存预算，SQLite 索引的可重建磁盘缓存

图像内存按**一个进程级的软预算**管理：缓存、可见图像、动画帧、解码临时估计和待写入数据都计入，同一份共享 buffer 只计一次；内存缓存是按解码成本管理的显式 LRU，不依赖 NSCache 的淘汰顺序（架构 §5.1）。磁盘上只缓存可重建的缩略图和小预览，原图不复制进缓存；元数据索引用系统 SQLite，载荷文件单独保存，文件名为稳定编码 `RenderKey` 的 SHA-256（架构 §5.1、§5.3）。限额跨窗口全局计算，不把每个窗口的限额相加（架构 §5.2；[ADR-002](./0002-session-isolation-shared-services.md)）。

这样选，是因为缓存必须有界、跨窗口共享、坏了能修：SQLite 由单一存储执行器串行访问、批量提交，不在 MainActor 上打开或查询；文件与数据库不能组成一个原子事务，所以接受可修复的孤儿文件，缓存出错永远不影响原图打开（架构 §5.3、§5.4）。

## Considered Options

- **只用 NSCache + 文件系统目录做缓存**：最简单，但淘汰顺序未定义、无法按字节计成本，也难以按修订失效。未选。
- **无磁盘缓存**：没有一致性问题，但每次重新打开目录，网格都要从原图重新解码缩略图。未选；P1 先不做磁盘缓存（开发计划 P1「暂不做」），P3 加入。

## Consequences

- 预算数值都是**待校准的设计参数，不是测量结果**（架构 §5.2）：图像总预算初始 `min(512 MiB, 物理内存的 8%)`，由 P0 用实际 RSS 与峰值校准（P0-05 记录实际字节）；磁盘缓存初始 2 GiB、可配置；不透明缩略图 JPEG 初始质量 0.8，经素材测试调整。
- P1-06 先做内存成本计量与最小有界缓存；P3-03 SQLite 最小索引（`key, itemID, revision, relativePayloadPath, byteCount, lastAccess, cacheVersion`）；P3-04 原子写入、崩溃修复与近似 LRU 水位淘汰；P3-05 清空 generation；P3-06 两窗口共享总预算；P3-08 按开发计划 §10 矩阵验证。
- 无授权时不交付缓存内容（架构 §5.3）；缓存不保留 EXIF/GPS；清除最近打开与清除图像缓存是两个动作。
- 磁盘缓存高水位与低水位的值不在本 ADR 定，由 P3-04 实现、P3-08 规模验证实测后写入验证记录（用户决定（2026-10-22））。
- 缓存放在 sandbox 容器的 `Library/Caches`：它可被系统清理，缓存本来就可删除重建（用户决定（2026-10-22））。
- Access Root bookmark、Library Folder、收藏与 Recent Item **单独存储**在 `Application Support`，与缩略图缓存的 SQLite 分开；「清除缓存」只动缓存，绝不丢失授权或用户数据（用户决定（2026-10-22）；P2-01、P3-14、P3-15）。
- 重评条件：真实规模（S2 及以上、P3-08 记录）需要额外索引能力，或单一存储执行器成为可测瓶颈时。
