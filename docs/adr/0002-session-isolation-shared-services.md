# ADR-002：窗口 Session 隔离，应用级服务共享

每个窗口有自己的 `@MainActor ViewerSession`（浏览器侧为对应的 Session），持有当前位置、目录快照引用、`selectedItemIDs` / `currentItemID` / `anchorItemID`、Preview Set、显示模式、缩放、未保存编辑、加载状态与请求代次；**ImagePipeline、缓存、FileAccess 和 WatchHub 在应用级共享**，但不共享「当前选中图片」（架构 §3.1）。两个窗口的导航、编辑、幻灯片计时互不污染；同一张图在两个窗口里只解码一次，按 `RenderKey` 去重，每个窗口持有独立订阅，一个窗口取消或关闭只减少引用（架构 §4.2、§8 场景表「两窗口请求同图」）。目录快照在窗口间共享只读数据，过滤条件与选择各自独立（架构 §6.1）。

这样选，是因为多窗口（P4-01）和桌面 pins（P4-02）要求状态不串窗口，而图像解码和内存是全应用最贵的资源：按窗口复制服务会重复解码、把每个窗口的限额相加，正违背 [ADR-005](./0005-memory-budget-sqlite-disk-index.md) 的全局预算。窗口本身由 AppKit `WindowCoordinator` 拥有（[ADR-001](./0001-appkit-owns-windows.md)），Session 不创建 NSWindow（架构 §2.1）。

## Considered Options

- **每个窗口一套完整服务**：隔离最彻底，但重复解码、监听与缓存，内存随窗口数线性放大（开发计划 §11 风险表「多窗口放大总内存」）。未选。
- **全局单一状态**（一个共享的当前图片/选择）：实现简单，但多窗口互相覆盖导航与编辑。未选。

## Consequences

- 组合根 `PicseeApp` 创建一份共享服务，注入到每个窗口的 Session；Application 层不建通用 DI 框架（架构 §2.1）。
- P1-05 的去重与订阅、P3-06 的「两个窗口共享限额」、P4-01 的「菜单作用于 key window、关闭一个窗口不取消其他窗口共享结果」都以此为前提；验收素材为 S6（开发计划 §10.1）。
- 授权检查按请求进行：新请求先取得 `AccessLease` 才查共享缓存，一个窗口不能借共享缓存绕过另一个窗口已失去的访问（架构 §3.3、§8）。
- 显示偏好（`DisplayPreferences`：外观、Filmstrip、工具常驻等）是 App 级设置，修改后**所有窗口即时同步**（用户决定（2026-10-22）；P1-09 的传播策略、账簿 PREF-04 以此为准）。
- 打开新输入时**默认复用当前窗口**，新开窗口作为用户设置（用户决定（2026-10-22）；P4-01 实现该设置）。
- 重评条件：真实多窗口内存数据（P3-08、P4 验收的 S6 记录）表明某项共享服务需要按窗口或按用途细分时。
