# ADR-003：Task/actor 协调请求，有界 OperationQueue 执行同步解码

请求的生命周期用 Swift Task / async-await 表达；缓存索引、去重表与调度状态由 actor 保护；`MainActor` 只做呈现。ImageIO、RAW 和大文件这类同步工作放进**专用、有界的 OperationQueue**（架构 §4.2）。关键原因写在架构里：把函数标为 async 或放进普通 actor，并不等于它不会阻塞 UI 或协作线程池；同步系统解码也未必能中途停止。所以要有一个并发上限明确、可观察、可取消排队工作的执行层。

取消的语义因此是「不再需要」：排队前、等待中、执行中取消与正常完成都要处理，包装 Operation 的 continuation 只完成一次；正在执行的解码继续占用工作槽和内存预约，直到真实返回再释放，结果按 `PresentationToken` 丢弃（架构 §4.2、§4.1）。跨执行器只传不可变请求与结果，不用整模块 `@unchecked Sendable`。

## Considered Options

- **全部用 async 函数 / actor 直接调 ImageIO**：代码最短，但同步解码会占住协作线程池，且没有显式并发上限。未选。
- **GCD 队列 + 信号量**：能限流，但取消、优先级提升和 continuation 只完成一次都要自己拼，测试面更大。未选。

## Consequences

- P0-06 先做受控 OperationQueue 包装，验收覆盖排队/执行中取消、continuation 只完成一次、内存预约释放（开发计划 §2、§10.3）；P1-04、P1-05 在其上建立视口预览、RenderKey 去重与 generation 校验。
- 调度默认值是**待 P0 实测的初始值**，不是测量结果（架构 §4.3）：可见缩略图全局上限初始 2、RAW/超大图重任务 lane 初始 1、相邻预取最多前后各 1、当前图片预留一个解码机会、磁盘写入后台串行。P0-05 记录实际字节与耗时，P0 验证记录（`docs/validation/P0.md`）写入需要更改的默认值（P0-07）。
- 最高优先级任务不能抢占已进入同步解码器的工作；不承诺硬实时，任何队列都不得一次为整个目录提交数千个解码任务（架构 §4.3）。
- 队列拓扑（用户请 Codex 参与评估后定，2026-10-22）：**一条有界解码 OperationQueue + 一个准入 actor**，磁盘缓存写入另用一条串行队列。待处理请求留在准入 actor 里，只有一次性拿齐所需许可（全局槽、所属 lane、重任务许可）与内存预约的请求才提交到队列；检查与占用之间不挂起。`maxConcurrentOperationCount` 等于全局上限 N，**N 已含为当前图预留的那一个**，不是「上限 + 1」。初始 N = 3：当前图预留 1，加可见缩略图上限 2；相邻预取与重任务都在这 3 个之内占位，不另加槽位，待 P0-05 校准。重任务是叠加约束，不是互斥类别：当前图如果是 RAW，同时占用当前优先级与那唯一的重任务许可。
  - 未选：每个 lane 一条 OperationQueue。各队列的上限加起来不等于全局上限；分头申请全局、lane 与内存许可会形成持有并等待的死锁；请求被提升优先级时在队列间移动，容易重复解码或泄漏预约。
  - 「当前图总有一个槽」只承诺**预留的准入机会**，以内存与重任务许可为前提，不承诺立即执行：后台 RAW 可能占着重任务许可，已取消但仍在解码的旧当前图也会占槽。内存不足时按降采样或明确失败处理（P1-04、P1-07）。
  - P0-06 用可控事件顺序的假执行器测试准入与取消，再用栅栏（不是 sleep）测试真实 OperationQueue 桥接。必须成立的不变量（数值取当时配置，不写死）：
    1. 跨所有窗口，已准入未结束的解码 ≤ N，非当前图解码 ≤ N−1，可见缩略图 ≤ 其上限，重任务 ≤ 重任务上限。计数按**准入时的许可类别**：一个解码在准入时占用的类别（当前图、可见缩略图、预取）在它真实返回前不变；之后用户切图、订阅优先级变化，只影响尚未准入的请求。例如两个窗口各有一个当前图解码时同时切图，两个旧解码仍算当前图类别，直到返回，新当前图要等它们释放。
    2. 准入原子地占用全部资源；取消绝不在解码真实返回前释放运行中的资源；内存预算是估算值，不是 RSS 保证。
    3. 每个已登记的 continuation 在成功、失败与各阶段取消（登记前、开始前、执行中）中恰好结束一次。
    4. 每个 RenderKey 只有一个进行中的解码；提升优先级不复制它；单个订阅者取消不影响其他订阅者；清理按 taskID 匹配。
    5. 准入按显式的优先级与公平规则进行：资源可用且前台需求有限时，符合条件的可见工作终将推进；预取可以被饿死。
- 并发上限、重任务 lane 与预取数量的实测**并入 P0-05**：P0-05 在记录解码字节与耗时之外，测量各 lane 上限对首图时间与内存峰值的影响，结果写入 `docs/validation/P0.md`（用户决定（2026-10-22））。
- 重评条件：新的 executor 或解码 API（例如可中途取消的系统解码、自定义 executor 能隔离阻塞工作）带来有实测证据的收益时。
