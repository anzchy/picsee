# ADR-004：文件系统是真相源，浏览由版本化快照驱动

picsee 原地浏览磁盘上的图片，不建必须先导入的资产库（架构 §1、§1.2「数据」）。FolderBrowser 接受 Access Root、递归选项、过滤与排序条件，异步分批枚举，返回带 `SnapshotVersion` 的不可变快照；旧扫描不得覆盖新导航（架构 §3.2、§6.1）。身份用 `ItemID`（优先卷标识与文件资源标识）与 `FileRevision`，不以数组下标或「路径相同」推断同一内容（架构 §3.2）。FSEvents 只是变化提示：事件合并后重扫受影响目录，事件丢失、卷变化、恢复前台时做有界全量核对（架构 §6.2）。

这样选，是因为开箱即用、不需要导入和同步是首发核心（架构 §1），而文件随时会被外部改名、替换、删除：只有把文件系统当真相、把应用内结构当可丢弃的快照，才能保证不串图、不出现永久重复或漏项（架构 §8 场景表）。Library 只是 Library Folder 的引用集合，「所有照片」是它们之上的视图，同样不导入、不复制图片（GLOSSARY.md；开发计划 P3-15）。

## Considered Options

- **导入式图库**（建自己的资产数据库，文件系统作为来源同步）：查询能力强，但要导入、要处理双向同步与冲突，偏离「打开即看」。未选；开发计划 §9 明确批量资产管理不在计划内。
- **把 FSEvents 当事务日志打补丁**：省重扫，但事件可能合并、丢失。未选。

## Consequences

- P2-02 分批枚举与快照代次、P2-04 扫描数量保护（初始 100,000 项，待 P0/P2 验证）、P2-07 WatchHub 共享监听与丢失后重扫、P2-08 外部删除/重命名/替换/卸载，都按此实现。WatchHub 的 debounce 初始 200 ms、最大等待 1 s 是待校准参数（架构 §6.2），由 P2-07 的真实 FSEvents 验证记录校准（P2 验证记录）。
- 扫描中保持当前 `ItemID`，完成后重新求位置；Preview Set 打开后不增长，删除或失去授权的项从中移除（开发计划 §1.4；GLOSSARY.md）。
- 磁盘上只允许存可删除重建的缓存（[ADR-005](./0005-memory-budget-sqlite-disk-index.md)），不存成为真相的目录索引。
- v1 **不持久化目录快照**：每次启动都重扫，文件系统是唯一真相源；Library 的计数在本次扫描完成前显示为未知（用户决定（2026-10-22））。
- 重评条件：产品转为大型资产管理库，或真实规模表明每次重扫无法满足 §10.2 的目录首批目标时。
