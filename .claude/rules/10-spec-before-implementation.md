# 新功能先定规格，再实施

用户 2026-10-28：「新功能在实施前一定要先经过 /grill-with-docs ，其次 /to-spec 最后 /to-tickets ，才能进入实施状态，如果没有的话，用askuserquestion tool 提示用户，不能只有模糊的plan就开始实施」

## 规则

新功能进入实施前，必须依次完成这三步：

1. **`/grill-with-docs`**：用户逐条确认决定，决定写进 GLOSSARY.md、ADR，或 grilling 记录。
2. **`/to-spec`**：写成 spec，发在 GitHub Issues。
3. **`/to-tickets`**：把 spec 拆成带验收标准和阻塞关系的 ticket（`ready-for-agent`）。

只有满足上面三步的 ticket，才能写实现 brief、派给实现者，或开始写代码。开发计划里的一行工作包、一段对话结论、一个原型，都不算规格。

## 缺了怎么办

发现要做的新功能缺少其中任何一步时，**停下，用 `AskUserQuestion` 提示用户**。说明缺哪一步，并给出选项，例如：
- 先跑 `/grill-with-docs`；
- 基于已有决定直接 `/to-spec`；
- 明确豁免。

不要只凭模糊的计划开始实施。`/grill-with-docs`、`/to-spec`、`/to-tickets` 由用户触发；需要时请用户运行，不要自己模仿它们的流程。

用户明确豁免时，把原话引用到对应 issue 里，再开始实施。

## 什么算新功能

- **算：** 新增用户可见的能力，或改变现有的用户可见行为、验收（「怎么确认」）、发布范围。包括新的页面、状态、设置项、菜单项、对外分发与更新流程。
- **不算：**
  - 修复不符合现有验收的 bug；
  - 不改变行为的重构；
  - 测试、工具、文档；
  - 已有 ticket 的审计修复轮。

拿不准时，按新功能处理，并用 `AskUserQuestion` 问用户。

## 已有工作

2026-10-28 之前创建的 issue，如果写有验收标准，并记录了用户决定（例如 #202、#113、#137、#141），可以继续实施。在这之后新开的功能，按本规则走。

## Codex

Codex 不加载这个文件，也没有 `AskUserQuestion`。delegator 只把满足本规则的 ticket 派给 Codex。Codex 发现任务缺少规格时，停下，把缺少的步骤写在最终回复里。
