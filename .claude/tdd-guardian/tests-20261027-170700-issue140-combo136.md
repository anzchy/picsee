# Test Matrix — WI-1: Grid Inspector follows watched image changes

Plan: `.claude/tdd-guardian/plan-20261027-170623-issue140-combo136.md`

## Unit: `CanvasWindowController` grid reconciliation → `InspectorModel.select`

**Law**: For a visible grid Current Item, the Inspector represents that selected entry's latest observed revision. Replaying a completed snapshot with the same selected revision is idempotent: it neither changes the displayed metadata nor starts another metadata read. A changed revision must invalidate the metadata key, whether the change appears only in the resource identifier or only in file size/modification date. This is an S5 state-transition law; a real filesystem and App host are needed to verify it.

### Case: Same-path atomic replacement updates the visible grid Inspector
- **Category**: failure
- **Lane**: integration (`app-red` manual lane)
- **Spec level**: S3 — reproduces the named stale-metadata failure with the selected ItemID and URL unchanged but the file resource revision changed.
- **Input**: Authorized temporary folder with `03-landscape.png` (landscape fixture) selected in a visible grid and `04-neighbour.png` beside it; Inspector open with the initial landscape pixel dimensions. Atomically rename a portrait fixture over `03-landscape.png`, then reconcile the watch and wait for a complete new source snapshot.
- **Expected output**: Grid stays visible; Current Item remains the original ItemID and path; Inspector's known `pixelWidth`/`pixelHeight` become the portrait fixture's dimensions, rather than retaining the landscape pair. The Inspector name remains `03-landscape.png`.
- **Observable side effect**: The real Inspector metadata reader reads the replacement and publishes a new `.known` value.
- **Assertion strategy**: Level 1 — assert the visible Inspector model's name and both new dimensions, plus the unchanged Current Item and visible grid; Level 2 — assert the read counter increases for the changed revision. The count supports, but cannot replace, the output assertions.
- **Mock boundary**: None. Use the real App controller, `FolderBrowser`, `WatchHub`, file access, `WindowInspectorReader`, ImageIO reader, and temporary files. A transparent counting decorator records reads without returning invented metadata.
- **Paired integration test**: This is the real integration case; no mocked boundary.
- **Refactor that would break this**: Any refactor that stops selecting metadata for the replacement revision, changes Current Item, or leaves the Inspector's pixel dimensions stale. Renaming a private helper alone would not break it.

### Case: New inode alone invalidates metadata when size and date match
- **Category**: property
- **Lane**: integration (`app-red` manual lane)
- **Spec level**: S5 — isolates the resource-identifier axis of the revision across an atomic replacement; size, mtime, URL, and ItemID are conserved.
- **Input**: Start with `portrait-2x3.png` (2,342 bytes) selected in the visible grid. Copy `landscape-3x2.png` (2,248 bytes) into a separate replacement file, append trailing bytes until it is exactly 2,342 bytes, verify ImageIO still reads its landscape dimensions, and set its modification date to the selected portrait file's date. Atomically rename it over the portrait path, then reconcile the watch and wait for the completed snapshot. Before and after, assert equal `fileSize` and modification date and unequal file resource identifiers.
- **Expected output**: Current Item and URL remain stable; the Inspector changes from portrait dimensions to landscape dimensions, and the per-selected-URL read count increases once for the new resource identifier.
- **Observable side effect**: A real metadata read of the replacement file publishes landscape dimensions despite equal size and mtime.
- **Assertion strategy**: Level 1 — assert real Inspector width/height and stable name/Current Item; Level 2 — assert one new read and the filesystem's equal-size/equal-date/new-inode preconditions. The preconditions prevent a size-only implementation from passing accidentally.
- **Mock boundary**: None — real FileManager/POSIX atomic rename, authorized folder, App grid, and forwarding counting reader.
- **Paired integration test**: This is the real integration case; no mocked boundary.
- **Refactor that would break this**: Dropping the resource identifier from the Inspector revision key would leave old portrait dimensions even though the inode changed.

### Case: Stable inode with changed size or date invalidates metadata
- **Category**: property
- **Lane**: integration (`app-red` manual lane)
- **Spec level**: S5 — isolates the in-place-content axis of the revision while preserving the file resource identifier, URL, and ItemID.
- **Input**: Start with selected `landscape-3x2.png` in the visible grid. Open the same file descriptor for write, truncate it and write the portrait PNG bytes in place (no rename), set a later modification date, and reconcile. Assert the file resource identifier remains unchanged while size and date change; wait for a completed new source snapshot.
- **Expected output**: Current Item and URL remain stable; the Inspector changes from landscape to portrait dimensions, and the per-selected-URL read count increases once.
- **Observable side effect**: A real metadata read publishes portrait dimensions after an in-place edit.
- **Assertion strategy**: Level 1 — assert the Inspector's new dimensions and stable Current Item/name; Level 2 — assert one new read and the filesystem's same-inode/changed-size-or-date preconditions.
- **Mock boundary**: None — real in-place filesystem write, authorized folder, App grid, and forwarding counting reader.
- **Paired integration test**: This is the real integration case; no mocked boundary.
- **Refactor that would break this**: Keying only on the resource identifier would preserve stale landscape dimensions after the in-place edit.

### Case: Unchanged watched reconciliation does not reread metadata
- **Category**: property
- **Lane**: integration (`app-red` manual lane)
- **Spec level**: S5 — idempotence of replaying a completed source snapshot while the selected entry's revision is unchanged, including a watched refresh caused by an unrelated file.
- **Input**: After the replacement case reaches `.known`, record the transparent reader's count. Trigger one reconcile without changing the selected file; trigger another by changing an unrelated image, keeping the selected file's resource identifier, size, and modification date stable. Wait for each completed snapshot and Inspector reconciliation.
- **Expected output**: The selected image's Inspector name and portrait dimensions remain unchanged after both transitions; its metadata read count remains at the baseline count.
- **Observable side effect**: No new metadata read for the selected image; the grid can update the unrelated entry.
- **Assertion strategy**: Level 1 — assert the Inspector's known metadata and selected Current Item after each refresh; Level 2 — assert the per-selected-URL read count is unchanged. These jointly distinguish a stale panel from a correct idempotent panel.
- **Mock boundary**: None. The counting decorator forwards every read to the real `WindowInspectorReader` and records URL/count only.
- **Paired integration test**: This is the real integration case; no mocked boundary.
- **Refactor that would break this**: A refactor that keys Inspector reads by snapshot generation or blindly sets `refresh: true` after every watched refresh would increment the counter while preserving output, so this case catches it.

### Case: Rename follows the grid Current Item
- **Category**: state
- **Lane**: integration (`app-red` manual lane)
- **Spec level**: S5 — same file resource moves from `03-landscape.png` to `03-renamed.png` while its Current Item identity is retained.
- **Input**: Move the selected replacement image to `03-renamed.png` within the authorized folder, reconcile the watch, and wait for the completed snapshot and Inspector selection.
- **Expected output**: Grid remains visible; Inspector name becomes `03-renamed.png`; dimensions remain the portrait pair; Inspector no longer names the old path.
- **Observable side effect**: A metadata read for the new URL may occur; the Inspector displays the moved file.
- **Assertion strategy**: Level 1 — assert new name and known portrait dimensions; Level 4 — assert grid visibility and Current Item identity.
- **Mock boundary**: None — real move and real App/grid/Inspector path.
- **Paired integration test**: This is the real integration case; no mocked boundary.
- **Refactor that would break this**: A refactor that reconciles grid entries but does not reselect the Inspector at the moved URL would fail the name assertion.

### Case: Deletion advances, then clears the grid Inspector
- **Category**: boundary
- **Lane**: integration (`app-red` manual lane)
- **Spec level**: S2 and S5 — the one-successor and zero-remaining-image partitions, with transitions through both.
- **Input**: With the renamed selected image and `04-neighbour.png` in the grid, delete the selected image and reconcile; then delete the neighbour and reconcile again.
- **Expected output**: After the first deletion the Inspector shows `04-neighbour.png` and its known dimensions, and the grid Current Item is that neighbour. After the final deletion the Inspector name is `nil`, value is `.unknown`, and the open Inspector shows no stale image metadata; the grid is still visible.
- **Observable side effect**: The Inspector reselects the successor, then cancels/clears metadata for an empty selection.
- **Assertion strategy**: Level 1 — assert successor name/known dimensions and final nil/unknown state; Level 4 — assert grid visibility and selected Current Item or empty selection as appropriate.
- **Mock boundary**: None — real deletions, watch reconcile, grid and Inspector.
- **Paired integration test**: This is the real integration case; no mocked boundary.
- **Refactor that would break this**: A refactor that keeps the deleted entry as Current Item, fails to choose the successor, or leaves stale metadata after the final deletion would fail.
