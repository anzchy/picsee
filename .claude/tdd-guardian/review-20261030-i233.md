### High — Some next-access failures still bypass File Grant revocation

Evidence: `Packages/PicseeKit/Sources/PicseeApplication/Viewer/InspectorMetadata.swift:60–63`, `App/UI/WindowInspectorReader.swift:30–34`, and `App/CanvasWindowController.swift:1980–2014`.

InspectorModel's current-generation error handler only updates its metadata value. WindowInspectorReader reports access failures only when a root read context exists. A File Grant metadata-only failure therefore cannot reach the new synchronous revocation boundary: the old image, identity and other presentation can remain visible after the failed access. Likewise, imageLoadFailed handles explicit needsFileReconnection and missing-path failures, but a generic decode/read failure while the file still exists falls through after clearing the canvas/title, retaining loader/Inspector identity and offering no reconnection. Foreground/wake reconciliation later detecting the problem does not satisfy detection at the failing next access.

This is an overall #233 AC-1/next-access correctness gap, already acknowledged in the amendment and ledger. It is not authorization to cross the implementer's ownership fence. Obtain the requested narrow ownership extension, then forward current File Grant reader failures into guarded access classification and the existing revocation boundary. Preserve cancellation/supersession suppression, bookmark rename/Trash policy, file-only scope, and ordinary errors for a readable corrupt image. The currently owned patch is useful but cannot be reported as the completed issue.
